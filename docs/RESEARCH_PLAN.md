# 组织提效 Agent Harness 市场调查计划

研究定位：面向软件交付组织，调查 Agent Harness 的需求、产品机制、采用条件及效率收益。

创建日期：2026-10-08。

## 1. 研究问题与当前进度

核心问题：在什么团队和任务中，Agent Harness 能以可接受的采用成本改善可验证的交付效率？

| 工作 | 当前状态 | 可交付内容 |
| --- | --- | --- |
| 项目发现与分类 | 已完成初版 | README 中 30 个项目、问题映射与官方来源 |
| 用户需求与采用条件 | 待验证 | 真实任务、现有解决办法、使用者与决策者 |
| 产品机制深入对比 | 待开展 | 状态、编排、验证、恢复、集成与维护差异 |
| 组织效率收益 | 待验证 | 有基线的使用记录、质量与成本结果 |
| 机会判断 | 待形成证据 | 按场景提出可验证的产品或开源方向 |

初始清单是项目发现结果。效果判断需要进一步取证。

## 2. 优先研究的用户与场景

以下是待验证的用户划分，用于安排调研。

| 用户 / 团队 | 优先观察的工作 | 关注的问题 |
| --- | --- | --- |
| 研发负责人或技术负责人 | 多模块开发、质量把关和交付进度管理 | 实际吞吐量、返工、人工监督投入 |
| 平台工程或研发效能团队 | 统一接入编码智能体与既有工具链 | 集成维护、权限、状态观测、成本控制 |
| 产品交付团队 | 跨会话开发、缺陷修复、重构和迁移 | 目标保持、交接、验收、异常恢复 |
| Harness 或智能体工具开发者 | 构建与维护运行框架 | 可复用组件、验证方法、故障定位 |

每个场景记录任务跨度、代码库规模、依赖关系、参与者、人工介入点和验收规则。长周期任务按跨会话、多阶段及交接需求描述，具体持续时间另行记录。

## 3. 产品研究记录

每个项目使用相同字段，便于比较。

| 字段 | 记录要求 |
| --- | --- |
| 项目与版本 | owner/repo、核对日期、所查 commit/tag、许可证及维护状态 |
| 用户与任务 | 使用者、采用决策者、主要交付场景 |
| 原始痛点 | 哪个步骤耗时或不可靠，当前解决办法是什么 |
| 核心机制 | 执行、状态、记忆、编排、验证、恢复、观测 |
| 工具链接入 | 依赖的模型、编码工具、Git、CI、任务系统与运行环境 |
| 产品边界 | 哪些能力已实现，哪些是示例、计划或文档声明 |
| 收益证据 | 来源、场景、基线、样本、质量条件及测量方法 |
| 采用成本 | 配置、部署、培训、权限、维护和运行成本 |
| 适用条件 | 在何种团队与任务中可能有用，何时成本可能超过收益 |
| 待验证问题 | 缺少哪些证据、下一步怎样验证 |

产品成熟度和采用事实分别记录。Star 数、功能数量、公开演示和组织中的实际使用效果各有不同含义。

## 4. 用户访谈提纲

访谈优先围绕最近一次真实任务展开：

1. 任务从需求到验收经历了哪些步骤？谁在每一步参与？
2. 使用智能体后，人工时间主要花在提示、监督、交接、审查还是返工？
3. 最近一次会话中断、任务停滞或交接失败造成了多少额外工作？
4. 目前如何定义“完成”？谁检查，依据是什么？
5. 多个智能体协作时，怎样分配任务、隔离修改和整合结果？
6. 团队已尝试哪些脚本、流程或产品？为什么继续使用或放弃？
7. 新工具怎样接入？谁负责部署、权限和长期维护？
8. 哪一种改善足以让团队采用？需要什么证据才能做决定？

记录受访角色、任务背景和证据。公开材料中使用匿名访谈编号，并明确标记自述与已验证事实。

## 5. 效率收益的测量口径

以固定验收规则下的任务为单位，同时观察结果、人工、质量和成本。

| 指标 | 建议口径 |
| --- | --- |
| 交付周期 | 任务满足执行前提开始，到通过既定验收的时间；另记等待与实际工作时间 |
| 验收吞吐量 | 固定观察周期内通过相同质量门槛的任务数 |
| 人工投入 | 提示、监督、交接、审查、返工所需的主动人工时间之和 |
| 人工介入 | 需要人修正方向、恢复运行或补充操作的次数；按原因记录 |
| 首次验收通过率 | 第一次提交验收即通过的任务数 / 已提交验收的任务数 |
| 返工成本 | 首次交付后为满足验收或修复缺陷投入的时间和费用 |
| 恢复成功率 | 遭遇预先定义故障后，在给定预算内仍通过验收的任务数 / 遭遇该故障的任务数 |
| 总成本 | 人工、模型、计算环境、工具费用，加上分摊的接入与维护投入 |
| 单位验收成本 | 观察期内全部尝试的总成本 / 通过验收的任务数；失败尝试也计入 |
| 逃逸缺陷 | 验收后在规定观察期内发现的缺陷，记录严重度与影响 |

选择一个团队可接受的主要指标，并同时记录质量与成本约束。缺少数据的项标记为未知。

对比前固定任务与验收规则，记录模型版本、工具配置、人员、并发量、预算及停止条件。按任务类型和难度分别报告结果，失败及未完成任务保留在记录中。样本有限时报告原始结果与不确定性。

## 6. 证据与结论

每条结论标明证据类型：

- **官方声明**：README、文档、发布说明或产品介绍，支持产品定位和声明能力。
- **可运行实现**：代码和复现记录，支持特定版本与配置下的能力。
- **用户自述**：访谈、Issue 或案例，支持特定用户的体验。
- **比较观察**：有基线、质量门槛和完整成本口径的对比记录。
- **研究假设**：根据已知材料提出的待验证判断。

公开结论附直接来源、核对日期、适用场景与仍缺少的证据。未收集的数据保留为空或标注待验证。

## 7. 形成机会判断

从真实工作中的重复痛点出发，检查现有产品覆盖、采用障碍和效率证据，逐步收敛可尝试的方向。

| 判断维度 | 所需证据 |
| --- | --- |
| 痛点是否持续 | 多次任务记录或多个用户独立描述 |
| 损失是否足够大 | 人工时间、等待、返工或失败成本 |
| 现有方案为何不足 | 可复现的缺口，或具体采用障碍 |
| 新方案怎样改善 | 明确机制及可观察的结果 |
| 第一版是否可验证 | 小范围接入方式、验收规则和成本预算 |

最终以“用户 + 场景 + 痛点 + 机制 + 证据”的形式提出产品建议，注明哪些部分仍是假设。
